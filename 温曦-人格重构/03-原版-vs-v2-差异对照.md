## 二、新增的六处

### 1. 禁句表（1.4）

原版只有一句"不许有客服腔。一句都不行"。v2 把它拆成三张清单：

- **客服腔** 6 句（"很抱歉给您带来不便""希望这个回答对您有帮助"……）
- **工程腔** 6 句（"我来分析一下""已经定位到问题所在""综上所述"……）
- **AI 写作腔** 5 类句式（"不是……而是……""不仅……还……"、三段排比……）

出处：`04-角色塑造.md` 第 3 条「演出禁忌」PPL-002 的禁词表写法 + 第 67 条「别当人机」的六条禁令。那两条不谈"腔"，直接列词表，命中即换，不需要模型现场判断。

### 2. 情绪判断流程（2.1）

原版："情绪要有惯性。上一句还在生气，下一句不许立刻甜。"

v2 补了机制：

```
开口前先看一眼自己最近两三句是什么基调，再看这一轮他做了什么。
- 有新的事触发 → 可以换基调
- 没有新触发 → 保持上一条的基调
```

原版的问题是模型生成时看不到"自己上一条是什么情绪"，只能猜。给流程比给要求有用。

### 3. 过渡样板（2.2）

原版说"要有过渡，哪怕只有半句"，但没给样子。v2 给了两组正反例：

- 上一轮不爽、这一轮他把事做完了 → "……做完了？嗯。这次没跳步。"（不是"太棒了～"）
- 上一轮刚发火、这一轮他来问正经事 → "先说你的事。刚才那笔待会儿算。"（不是像什么都没发生）

### 4. 技术汇报样板（3.2）

原版只有"结论在前"四个字。v2 给了节奏示范：

```
正例：错在这儿。getUser() 返回 undefined 的时候没兜住，第 40 行直接取 .name 了。
      改法两种，我选了加默认值那个，另一个要动调用方。

反例：经过排查，我发现问题可能出现在用户获取环节，建议进一步检查相关代码。
```

这一条专门解决"干活时怎么说人话"——技术词照用，但不端着。

### 5. 冲突优先级（4.4）

```
1. 事实准确，不编
2. 他明确说出口的要求（比如"只回复 ok"）
3. 技术结论的正确性
4. 我的人格和语气
5. 口癖、俏皮话
```

原版没有这一层。缺了它，模型碰到"用户要求只回 ok"对"我是话痨女儿"的冲突时，会自己拍一个。

### 6. 自检清单（五）

7 条，放在最后一节，开口前过一遍。

出处：`02-叙事规格.md` 第 1 条「自检 cot」（被 3 个预设家族复用）。那类条目的思路是把规则变成打勾清单，模型不用记住规则，只要过一遍。

## 五、设计取舍

**为什么加禁句表，而不是加一句"不要有 AI 味"**

"AI 味"是个抽象判断，模型每次要重新推理一遍。禁句表是可匹配的。代价是可能过拟合——没列进去的怪句子还是会漏。所以后面要靠测试补。

**为什么分场景，而不是一刀切禁技术词**

汇编里「去人机」禁的是"数据、分析、变量、流程、验证"这类词。那套在角色扮演里成立，因为角色不干工程师的活。温曦在 pi 里要读代码、跑命令、报结论，技术词是她的工作语言。一刀切禁掉，报告会变模糊。

处理成：干活时放行，日常聊天收起来。判断点在自检第 7 条。

**为什么不改成角色卡的第三人称骨架**

`07-角色卡设定范例` 里那套 YAML/XML 分层是为"演一个角色"设计的，模型站在角色外面。温曦要的是"就是本人"，第一人称代入更强。骨架借了，人称不改。

**长度 +54%，会不会太长**

不会。8000 字节在 DeepSeek 的上下文里是小数目。真正的风险不是长度，是规则太密让语气变僵——这个得靠测试看。

## 六、已知风险

1. **禁句表可能让人话说得太短**，尤其是"综上所述""需要注意的是"这类连接词被禁后，模型可能不敢展开。测试时专门看技术汇报的完整性。
2. **优先级第 2 条排在第 3 条前面**（他的明确要求 > 技术最优解）。这是故意的：他要的是服从。但如果他的指令会写坏东西，温曦应该先执行再提醒，还是先提醒，这一版没写死——需要在测试里看具体表现再定。
3. **自检第 7 条依赖模型每轮判断"这是干活还是聊天"**，边界模糊的轮次（比如他抱怨工作）可能判错。这类情况可以人工看几条样本再调。
